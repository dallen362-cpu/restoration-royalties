## 0. Important framing (read first)

- **Use the API, not the portal login.** Automating the human login at portal.vitelity.net (storing/replaying the portal password, screen-scraping) is brittle, against typical provider terms, and a security liability. Vitelity exposes a sanctioned API for exactly this. This spec uses that.
- **Credentials are generated by you in the portal, stored server-side by Telvergence.** A developer enables API access and creates an API username/password in the Vitelity account, then Telvergence's backend holds those as secrets. (Claude does not log into the portal or handle the portal password.)
- **Vitelity is now an Inteliquent / Sinch company.** The legacy v1 command API is still the workhorse for provisioning; a newer v2 JSON API exists but currently covers LNP (porting) only. Confirm current endpoints/limits against your account's API page (apihelp.vitelity.net) before go-live — exact base host and a few parameter names should be verified there.

## 1. The two API generations

| | **v1 (legacy command API)** | **v2 (JSON API)** |
| :-: | :-: | :-: |
| Docs | apihelp.vitelity.net | docs.vitelity.net |
| Style | HTTP GET/POST, cmd= selects the function; responses are XML/text | RESTful JSON |
| Auth | login + pass params (API sub-user credentials) | HTTP Basic auth (account/API username + password) |
| Coverage | **Full provisioning** — DIDs, routing, sub-accounts, CNAM, E911, SMS, fax, billing | **LNP/porting only** at first release |
| Use for this project | **Primary** — all DID provisioning/routing | Use for port-in orders as it matures |

**Recommendation:** Build the Telvergence provisioning service on **v1** for ordering/routing now; adopt **v2** endpoints for any function as Vitelity migrates them to JSON.

## 2. Auth & connection model

- **Endpoint (v1):** HTTPS POST to the Vitelity API host (confirm exact host on your API page; historically https://api.vitelity.net/api.php). SMS may use a separate SMS endpoint — confirm.
- **Required params on every call:** login (API username), pass (API password), cmd (command), plus command-specific params. xml=yes returns structured XML.
- **Hardening:**
  - Create a **dedicated API sub-user** (not your main login).
  - **IP-allowlist** the API user to Telvergence's server IPs in the portal.
  - Store VITELITY_API_USER / VITELITY_API_PASS in a secrets manager (never in code or the repo).
  - Log every call + response for audit; respect rate limits (e.g., cdrlist only every 5 minutes).

## 3. Command map (the functions Telvergence will call)

Grounded in Vitelity's documented v1 command set.

**DID inventory / search**

- listnpa — available local numbers for a specific **area code** (e.g., 954, 786) ← core for local-presence pools
- listnpanxx — available numbers for a specific NPA-NXX (tighter geo match)
- listlocal — all local DIDs in stock
- listratecenters / listavailratecenters — ratecenters by state / in stock
- listspecificlocal — rate for a specific DID; listdids — everything you currently own

**DID ordering / lifecycle**

- getlocaldid — **order a specific local number** ← core
- gettollfree / requestvanity — toll-free / vanity
- localbackorder (+ localbackorderrate) — backorder a ratecenter not in stock (e.g., thin 754 supply)
- removedid — retire a DID (e.g., one flagged "Spam Likely")
- didforcebilling — force a DID's billing to a specific sub-account

**Routing & sub-accounts** (match each DID to the right agent/queue)

- addsubacc — create a SIP sub-account / peer ← one per queue or agent
- subaccounts — list them; delsubacc — delete (irreversible)
- reroute — point a DID at a sub-account or IP ← core
- massreroute — reroute many DIDs at once; routeall — route everything
- migratedids — move DIDs between sub-accounts (rebalancing)
- callfw — call-forward a DID; failover — set failover target

**Branded caller ID (anti "Spam Likely")**

- lidb — **set the CNAM/caller-ID name** (e.g., "RESTORATION ROYALTY") ← core
- lidbavail / lidbavailall / lidbcheck — availability & status
- cnamenable / cnamdisable / cnamstatus — outbound CNAM dip control
- *Note:* CNAM sets the displayed **name**. Full **STIR/SHAKEN attestation** and branded call display (the real fix for spam-labeling) are handled at the Inteliquent/Sinch platform level and may require an order/ticket rather than a v1 call — confirm with Vitelity support and factor into go-live.

**E911 (legally required on any calling DID)**

- e911checkaddress → e911send → e911getinfo / e911delete

**SMS (optional, consented contacts only)**

- checksms → setsms (enable) → smsenableurl (deliver to a Telvergence webhook) → sendsms; smsdids lists SMS-capable numbers

**Billing / reporting**

- balance, cdrlist (+ resetcdrlist), didcdrdetail (per-DID usage/cost), subaccountcdrdetail (per-agent)

## 4. Provisioning workflow (maps to the campaign)

**Step 1 — Sub-account structure.** Create SIP sub-accounts for the dialer queues/agents: addsubacc → RR-BROWARD-Q, RR-DADE-Q, RR-IN-TRACK, (and per-agent peers as needed).

**Step 2 — Order local-presence DID pools.** For each target area code, search then order:

- Broward: listnpa(npa=954) and listnpa(npa=754) → getlocaldid ×6–10 each
- Miami-Dade: listnpa(npa=305) and listnpa(npa=786) → getlocaldid ×6–10 each
- Palm Beach: listnpa(npa=561) → getlocaldid ×2
- If a ratecenter is dry (754 can be), use localbackorder.

**Step 3 — Route DIDs.** reroute (or massreroute) each Broward DID → RR-BROWARD-Q, each Dade DID → RR-DADE-Q; inbound tracking numbers → RR-IN-TRACK.

**Step 4 — Brand caller ID.** lidbavail then lidb(name="RESTORATION ROYALTY") on every outbound DID; open the STIR/SHAKEN attestation request with Vitelity/Inteliquent.

**Step 5 — E911.** e911checkaddress (RR business address) → e911send on each DID. **Do not skip — required.**

**Step 6 — SMS (optional).** Only on consented numbers: setsms → smsenableurl(https://app.telvergence.com/webhooks/vitelity-sms).

**Step 7 — Monitor & rotate.** Nightly balance + cdrlist; if a DID gets spam-flagged, removedid and getlocaldid a replacement, then reroute. Use didcdrdetail / subaccountcdrdetail for per-number and per-agent reporting back into Telvergence's dashboard.

## 5. Reference implementation (Node.js skeleton)

```js
// vitelityClient.js — thin wrapper over Vitelity v1 command API
import axios from "axios";
import { parseStringPromise } from "xml2js";

const BASE = process.env.VITELITY_API_URL;     // confirm exact host on apihelp.vitelity.net
const AUTH = {
  login: process.env.VITELITY_API_USER,        // dedicated API sub-user
  pass:  process.env.VITELITY_API_PASS,        // stored in secrets manager
};

async function call(cmd, params = {}) {
  const form = new URLSearchParams({ ...AUTH, cmd, xml: "yes", ...params });
  const { data } = await axios.post(BASE, form.toString(), {
    headers: { "Content-Type": "application/x-www-form-urlencoded" },
    timeout: 20000,
  });
  const json = await parseStringPromise(data, { explicitArray: false });
  return json;
}

export const vitelity = {
  listNpa:      (npa)              => call("listnpa", { npa }),
  orderLocal:   (did)              => call("getlocaldid", { did }),
  removeDid:    (did)              => call("removedid", { did }),
  addSubacc:    (name, pass)       => call("addsubacc", { name, pass }),
  reroute:      (did, sub)         => call("reroute", { did, sub }),
  massReroute:  (dids, sub)        => call("massreroute", { did: dids.join(","), sub }),
  setCnam:      (did, name)        => call("lidb", { did, name }),
  e911Check:    (addr)             => call("e911checkaddress", addr),
  e911Send:     (did, addr)        => call("e911send", { did, ...addr }),
  enableSms:    (did)              => call("setsms", { did }),
  setSmsUrl:    (did, url)         => call("smsenableurl", { did, url }),
  balance:      ()                 => call("balance"),
};

// provisionPool.js — order N local DIDs for an area code and route them to a queue
import { vitelity } from "./vitelityClient.js";

export async function provisionPool({ npa, count, subAccount, cnam, e911 }) {
  const avail = await vitelity.listNpa(npa);
  const numbers = extractDids(avail).slice(0, count);   // parse per your XML shape
  const ordered = [];
  for (const did of numbers) {
    await vitelity.orderLocal(did);
    await vitelity.reroute(did, subAccount);
    await vitelity.setCnam(did, cnam);                  // "RESTORATION ROYALTY"
    await vitelity.e911Send(did, e911);                 // required
    ordered.push(did);
  }
  return ordered;
}

// Example: provisionPool({ npa: "954", count: 8, subAccount: "RR-BROWARD-Q",
//                          cnam: "RESTORATION ROYALTY", e911: RR_ADDRESS });
```

*Parsing note:* v1 responses are XML/text, so build your extractors around the actual response shape (test one listnpa call and inspect it). When Vitelity moves a function to the v2 JSON API, swap that one method to the JSON endpoint with Basic auth.

## 6. Security, compliance & guardrails

- **Never** store or replay the **portal** password or scrape the member UI — API credentials only, in a secrets manager, IP-allowlisted.
- **Irreversible commands** (delsubacc, removedid) must require a confirmation flag in Telvergence's code and an audit-log entry before execution.
- **E911 is mandatory** on any DID used to place/receive calls — wire e911send into the provisioning flow, not as an afterthought.
- **Spam mitigation = CNAM (lidb) + STIR/SHAKEN attestation.** Set CNAM via API; open the attestation/branded-calling setup with Vitelity/Inteliquent support.
- **Calling-law posture is unchanged by automation:** provisioning numbers faster doesn't change TCPA/FTSA — keep dialing manual to business lines, suppression list enforced, FL telemarketer registration in place.
- **Rate limits:** honor documented intervals (e.g., cdrlist every 5 min); add retry/backoff and idempotency keys so a retried order doesn't double-buy.
